# Security review — 2026-09-14

An identity-and-security read of the implementation and the documentation,
against `sha-6606da9` (migrations V58). It deliberately looks for things
**not** already in `hardening-backlog.md`; where a known item deserves sharper
framing, that is said and the existing ID is reused.

## Posture, stated plainly

The security engineering here is well above what a platform of this size
usually carries. Several controls are not merely present but correctly
reasoned:

- **Authorization-code replay revokes the token family it issued**, rather than
  only refusing the second exchange. The comment explains exactly why refusing
  is not enough — whoever exchanged first holds live tokens — and it uses a
  `REQUIRES_NEW` revoker so the rejection cannot roll the containment back.
  That is a level of care most implementations do not reach.
- **WebAuthn signature-counter regression disables the factor** and audits it,
  which is the only cloning signal the protocol offers.
- **PKCE gaps are metered, not silently tolerated** (`sso.oidc.pkce.missing`),
  with the backfill gated on the meter reading zero. Same pattern for legacy
  user-verification. This is the right way to tighten a live system.
- **Password reset** bumps `token_version`, revokes refresh tokens, clears the
  lockout, and is single-use against a hashed token.
- **Algorithm confusion is closed** by construction: jjwt 0.12 `verifyWith(SecretKey)`
  refuses a token whose `alg` does not match the key type, `none` included.

The findings below should be read against that. Nothing here suggests the
system is weak; they are the next layer down.

## New findings

### B-OIDC-6 · High · Single-use enforcement is a check-then-write race

`OidcAuthorizationService.exchangeCode` reads the code row, tests
`row.getUsedAt() != null` in Java, and later writes `usedAt`. The method is
plain `@Transactional` — READ COMMITTED on Postgres — with no `@Version`, no
`SELECT … FOR UPDATE`, and no conditional `UPDATE … WHERE used_at IS NULL`.

Two concurrent redemptions of the same code therefore both observe
`used_at IS NULL`, both pass the guard, and both mint tokens. The second
`UPDATE` blocks on the row lock and then overwrites — it does not re-evaluate
the condition, because the condition was evaluated in application code against
an earlier snapshot.

**Why this one matters more than its class usually does.** The replay
detection it defeats is the best control in the file. An attacker who steals a
code and races the legitimate client gets tokens *and* leaves the family
un-revoked, so the victim sees a successful login and no alarm fires — which is
precisely the scenario the family revocation was written to catch. The
protection is strongest against the slow attacker and absent against the fast
one.

**Fix.** Make the consume atomic and branch on rows affected:

```sql
UPDATE oauth_authorization_codes
   SET used_at = now()
 WHERE id = :id AND used_at IS NULL
```

Zero rows affected means someone else took it — run the existing replay path.
`@Version` on the entity is an acceptable alternative; a serializable
transaction is not, at this call rate, worth the retry handling.

**Not empirically raced.** This is a code-level reading, not a demonstrated
exploit. A concurrency test belongs with the fix.

### B-AUTH-6 · High · Refresh-token rotation has the same race

`RefreshTokenService` follows the identical read-check-write shape against
`usedAt` / `revokedAt`, with the same annotations and the same absence of
locking. The consequence is the same and arguably worse: refresh reuse
detection is the control that turns a stolen long-lived credential into a
contained incident, and a race through it leaves two live families with no
signal.

Fix both together — they are one defect with two instances, and a fix applied
to only one will read as complete.

`PasswordResetService.resetPassword` shares the shape. The consequence there is
minor (two concurrent resets, last write wins), so it does not warrant its own
severity, but it should be fixed in the same pass so the pattern does not
survive anywhere.

### B-AUTH-7 · Medium · The refresh cookie carries no `SameSite`

`AuthService.writeSessionCookie` sets `SameSite=Lax` deliberately, with a
comment explaining that Strict would break the OIDC top-level redirect.
`writeRefreshCookie`, immediately above it, sets `HttpOnly`, `Secure`, `Path`
and `Domain` — and no `SameSite` at all.

So the **longer-lived, higher-value** credential is the one left to browser
defaults. Chrome's default is Lax and most current browsers agree, but relying
on a default for the credential that survives the session is the wrong way
round, and the inconsistency reads as an oversight rather than a decision.

`/api/auth/refresh` is never a legitimate cross-site top-level navigation
target, so this cookie can take **`SameSite=Strict`** — strictly better than
the session cookie's Lax, and it costs nothing.

### B-OIDC-7 · Medium · Client secrets are reversibly encrypted where they could be hashed

`OidcClient.clientSecret` is stored under `EncryptedStringConverter` —
recoverable by anyone holding the database and `app.crypto.secret`.

The argument against is in the same entity, eleven lines below. The RFC 7592
registration access token on that class is stored as a SHA-256 hash, with this
comment: *"Hashed for the same reason refresh tokens are: it is a bearer
credential that grants control of a client registration, so a database dump
should not be enough to take one over."*

Every word of that applies to `client_secret`. It is only ever compared, never
re-displayed — `OidcClientService` shows it once at creation and once at
rotation, exactly like the registration token. There is no flow that needs the
plaintext back, so the reversibility buys nothing and costs the property that
the neighbouring field was deliberately given.

Migration is the real work: hash on next rotation, keep verifying the encrypted
form until a client has rotated, and meter the stragglers — the same pattern
already used for PKCE and legacy UV.

### B-PRIV-1 · Medium · No retention enforcement, and two tables grow without bound

`docs/compliance/privacy-and-data-retention.md` is commendably honest: it marks
the schedule PROPOSED and states outright that **no scheduled purge job exists
for any category except order expiry**. The finding is that this is still true
months later, and two of the categories grow with traffic rather than with
users:

- **`refresh_tokens`** — rotated on every refresh and never purged after expiry.
  One row per refresh, forever. At a 15-minute access token this is the
  fastest-growing table in the system.
- **`audit_events`** — explicitly append-only and never deleted. Correct as a
  security posture, unbounded as an operational one, and under POPIA
  §14 an indefinite retention of `ipAddress` and `userAgent` needs a stated
  basis rather than an absent policy.

Both now have monitoring behind them, so this is visible before it is urgent —
but a purge job for expired refresh tokens is a small, safe change and should
not wait for the full retention schedule.

### B-GOV-1 · Medium · No vulnerability disclosure channel

The repository is **public** and the product is an identity platform. There is
no `SECURITY.md`, and `https://www.weldforge.org/.well-known/security.txt`
returns 404.

A researcher who finds something has no documented way to report it, which
leaves them guessing an address or publishing. For an IAM vendor this is also
the first thing an enterprise security reviewer looks for, and its absence is
read as immaturity regardless of how good the code is.

Both artefacts are cheap: `SECURITY.md` with a contact, a scope statement and a
response-time commitment; `security.txt` per RFC 9116 with `Contact`,
`Expires`, `Preferred-Languages` and a `Policy` link.

### B-GOV-2 · Medium · The threat model analyses a decommissioned architecture

`docs/threat-model.md` still describes the platform as *"one Spring Boot jar +
PostgreSQL on GKE Autopilot (GCP …)"*, diagrams *"GKE ingress / nginx"*, and
places the platform HMAC in *"GCP Secret Manager `wf-jwt-secret`"*. None of
that has been true since 2026-08-31.

A stale reference in a runbook wastes someone's afternoon. A stale
**architecture** in a threat model invalidates the reasoning built on it: trust
boundaries, blast radius and the network path are all drawn against a system
that no longer exists. It also cannot cover attack surface introduced since —
internet-facing Grafana and ntfy, the anonymous order endpoint, live per-tenant
subdomains.

`docs/compliance/privacy-and-data-retention.md` carries eight GCP references
including Cloud SQL backup retention, with the same problem in miniature.

### B-PROV-2 · Low · A 72-hour anonymous slug reservation invites squatting

Self-reported: I introduced this today. When no payment gateway is configured,
`OrderService.createOrder` now records the order and holds the requested tenant
slug for **72 hours**, on an anonymous, unverified request. Before the change
the row was only written when a gateway existed, with a 10-minute hold.

Rate limiting caps the volume, but a determined caller can still park desirable
slugs — `acme`, a competitor's name — and renew every three days. The contact
email is never verified, so there is no cost to the squatter.

Options, cheapest first: shorten the manual-path hold; make it *soft* (record
the preference without blocking others until a human confirms); or verify the
contact email before the reservation takes effect.

It also made the privacy documentation stale in the same motion — the retention
table still says *"slug reservation 10 min TTL"*.

## Known items that deserve sharper framing

**B-AUTH-5 — disabling MFA is easier than using it.** `MfaService.selfReset`
wipes every factor on a password check alone, with no rate limit and no second
factor. A control should be at least as hard to remove as it is to satisfy;
here it is strictly easier. Requiring a current factor — or a backup code — to
drop MFA closes it.

I checked whether this chains into an email-only takeover: it does not.
`resetPassword` mints no session, so MFA still gates the subsequent login. The
finding stands on its own, at its existing severity.

**B-JWT-2 — one HMAC, four holders, no key ring.** `app.jwt.secret` signs every
session JWT and is mirrored to all three Tech Metropolis consumers. With no
key-ring, rotation is not a maintenance task, it is a synchronised outage
across four codebases in two organisations — which is why it has not happened.
Accept-old-while-signing-new is the unlock, and it is a prerequisite for
treating a suspected leak as recoverable rather than catastrophic.

**Rate limiting is per-instance** (`RateLimitingService`). Documented today in
`docs/scaling.md` and in the class itself; repeated here because it is a
security property, not only a scaling one: raising replicas multiplies every
configured limit and nothing in the configuration reveals it.

## Checked and found sound

Recorded so the next reviewer does not re-derive them:

- **Authorization code binding** — tenant and client re-checked at redemption,
  `redirect_uri` exact-matched, expiry enforced, PKCE verified, public clients
  refused without a challenge, confidential secrets compared in constant time.
- **Algorithm confusion** — closed by jjwt 0.12 key-type binding.
- **Privilege escalation via role assignment** — `setAdminRole` requires
  super-admin, resolves the target within the caller's *resolved* tenant so the
  audited cross-tenant path is honoured, bumps `token_version`, syncs the global
  membership and audits. Lockout recovery exists: three super-admins in
  production and `APP_ADMIN_BOOTSTRAP_SUPER_ADMIN_EMAIL` is configured.
- **Password reset** — hashed single-use token, session termination on both the
  access and refresh sides.
- **WebAuthn** — UV required for new enrolments, legacy exceptions metered,
  counter regression disables and audits.
- **Slug enumeration via the order endpoint** — not a new exposure; tenant
  existence is already discoverable from public OIDC discovery.

## Suggested order

1. **B-OIDC-6 / B-AUTH-6** — the atomic-consume fix, both call sites, with a
   concurrency test. Small change, and it restores a control that is currently
   conditional on the attacker being slow.
2. **B-GOV-1** — `SECURITY.md` and `security.txt`. An afternoon, and it is the
   most visible gap to an outside assessor.
3. **B-AUTH-7** — `SameSite=Strict` on the refresh cookie. One line.
4. **B-GOV-2** — rewrite the threat model against k3s. Until then it should
   carry a banner saying which architecture it describes, so nobody reasons
   from it.
5. **B-PRIV-1** — expired-refresh-token purge first; the full retention
   schedule can follow.
6. **B-OIDC-7**, **B-AUTH-5**, **B-PROV-2**, **B-JWT-2** — each real, none
   urgent.
